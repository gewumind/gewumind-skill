## 1. 菜单组件树

菜单组件树按 **顶级分组 → 组件 → 视图组件** 三级组织：

- **顶级分组**：左侧菜单栏一级菜单，对应路由 `/{module}`
- **组件（页面）**：左侧菜单栏二级菜单，对应路由 `/{module}/{page}`
- **视图组件（第三级）**：页面内部的子视图，对应 `/{module}/{page}/{view}`，列出页面包含的每个视图组件

> **推荐格式**：用「菜单树 vs 路径树」左右对照表格（见下方 ui.md 文件示例），左列保留 `├─` `└─` 树形，右列给出完整路径。这样：
> - 既能看菜单层级（点开哪个菜单是哪个页面）
> - 又能直接得到 SFC name 和 route path（用于生成 menu SQL）
> - 同时方便和 api.md 的「文件夹 → API 路径」对照

**路径拼接规则**（第三级完整路径）：
- 顶级：`/{module}`
- 二级（组件）：`/{module}/{page}`
- 三级（视图组件）：`/{module}/{page}/{view}`
- 例：设备列表的列表视图 → `/device/list/list`；设备列表的表单视图 → `/device/list/form`

**视图组件类型**：
- `list` — 数据表格（table）
- `form` — 弹窗表单（dialog/modal）
- `tree` — 树形数据（tree）
- `publish` — 发布操作（publish）
- `mapping` — 映射关联（mapping）
- `control` — 控制面板（control panel）
- `stats` — 统计面板

> **路径格式规则**：
> - 顶级路径：`/{module}`（如 `/device`, `/content`, `/setting`），**不是** `/device-management`
> - 二级路径（组件）：`/{module}/{page}`（如 `/device/list`, `/content/notice`），**不是** `/device-list`
> - 三级路径（视图组件）：`/{module}/{page}/{view}`（如 `/device/list/list`, `/device/list/form`），**不是** `/device-list-list`
> - 菜单树里第二级写 `/{page}`（相对于顶级），第三级写 `/{view}`（相对于第二级）；完整路径 = 拼接得到
> - 菜单的英文段必须与 api.md 路径树**完全一致**。这是后续 LLM 生成 .ms 和 menu SQL 的唯一依据。

## 2. 每个页面格式

> ⚠️ **§2 每个页面必须按以下固定结构写**，后续生成 .vue 时严格按"字段"表（**类型**列）选组件。**字段表与 database.md 同表字段表完全对齐**（字段名、类型、必填）——不准自由发挥，不准在 ui.md 写 database.md 里没有的字段。

```markdown
### 2.2 设备列表 (/device/list)

#### 2.2.1 列表 (/device/list/list)

**展示列**: sn, name, model, status, office_name, last_online_time

**查询条件**: sn(模糊) / model(精确) / status(精确) / office_id(树选)

**操作流**:
1. 进入页面 → 加载设备列表（分页表格）

3. 勾选多行 → 点「批量删除」→ 二次确认 → 逻辑删除

**数据权限**: 列表数据默认按当前用户组织范围过滤，页面提供组织选择器可切换

+---------------------------------------+
| SN: [___] 型号:[▼] 状态:[▼] [查询]   |
+------+------+------+--------+--------+
| SN   | 名称 | 型号 | 状态   | 操作    |
| T100 | 站台 | T100 | 在线   | [编辑]  |

```

#### 2.2.2 表单 (/device/list/form)

**字段**（**必须用 4 列表格：字段 / 类型 / 必填 / 说明**，与 database.md 对齐）:

> ⚠️ **唯一允许的格式**：4 列（字段/类型/必填/说明）。**严禁**5+ 列（含默认值、字典、备注等多余列）或 3- 列简化写法。validateDocs 会报错让 LLM 重写。
> - ❌ 错误：`| 字段 | 类型 | 必填 | 默认 | 说明 |`（5 列含默认）
> - ❌ 错误：`| 字段 | 类型 | 必填 | 说明 | 字典 |`（5 列含字典）
> - ✅ 正确：`| 字段 | 类型 | 必填 | 说明 |`（4 列）
| 字段 | 类型 | 必填 | 说明 |
| sn | string(32) | 是 | 设备 SN |
| name | string(100) | 是 | 设备名称 |
| model | select | 是 | dict: device_model |
| installLocation | tree-select | 否 | 引用地点表 |

> **类型列必须从以下固定值里选**（与 gewumind-boot 组件库对齐，避免 LLM 自由发挥）：
> - `string(N)` / `int` / `datetime` / `text` — 普通输入框
> - `select` — 下拉（必须配 `dict: xxx` 或 `options: /url/options`）
> - `tree-select` — 树选（必须配关联表）
> - `date` / `datetime` — 日期/日期时间选择器
> - `upload` — 文件上传
> - `editor` — 富文本编辑器
> - `switch` — 开关
> - `radio` — 单选
> - `checkbox` — 多选

**按钮**: 保存 / 取消

**操作流**:
1. 点「新增」→ 打开弹窗表单 → 填写 → 保存 → 关闭弹窗 → 刷新列表
2. 点「编辑」→ 打开弹窗表单（回填数据）→ 修改 → 保存 → 关闭弹窗 → 刷新列表

## 3. 页面完整性：菜单树 → §2 全量对照

> ⚠️ **菜单组件树有多少个页面节点，§2 页面详情就必须有多少个 `### 2.x` 节**。

**规则**：
1. 写完菜单树后，统计**叶子节点数**（即实际页面，不包括顶级模块）
2. 每写完一个页面，在 `### 2.x` 标题后的括号里标注路径（如 `### 2.1 首页 (/home)`）
3. 调 `validateDocs` 前确认叶子节点数 = `### 2.x` 节数
4. 不够 → 继续写，**不允许跳过或提前结束**

**典型遗漏**：
- ❌ 菜单树有 21 个页面，ui.md 只有 4 个 → 漏了 17 个
- ❌ 写了设备管理全部页面，但内容管理/升级管理/系统设置一个没写

## 3.1 写入策略：**合并写**多个小节到一次 writeDoc

> ⚠️ **关键约束**：避免 LLM 单次输出超过 provider 配置的 max_tokens（被 `finish_reason=length` 截断）。但**不要每个小节就调一次 writeDoc**——每个 writeDoc 都有 reasoning_content + tool_call JSON 元数据开销，**浪费 token**。

**合并写以减少 token 浪费**：

```
❌ 错误：每页独立 writeDoc（20 次往返 + 20 次元数据浪费，$0.02+）
✅ 正确：合并多页到一个 writeDoc（3-4 次往返就够，省 70% token）
```

**单次 writeDoc 调用规范**：
- `content` 字符数 = `max_tokens × 4 × 0.8`（留 20% 余量给 tool_call JSON）
- **8K tokens** 配置下单次 ≈ **~26000 字符**（≈ 3-5 个完整 ui.md 页面 + 各自的线框图）
- **16K tokens** 配置下单次 ≈ **~52000 字符**（≈ 6-8 个完整 ui.md 页面）
- **在不确定 max_tokens 时，保守起见单次 < 15000 字符**（避免被截断导致代码块未闭合）
- 一次写多个 `### 2.x` 章节（按文档结构顺序）——不是每个小节写一次

**典型示例流程**（20 页 + §3 组织机构 ≈ 100K 字符文档，假设 16K tokens）：
1. **writeDoc overwrite 初始化**：写文档标题 + §1 菜单树 + §2.1-§2.6 前 6 页（~30K 字符）
2. **writeDoc append**：写 §2.7-§2.16 中 10 页（~50K 字符）
3. **writeDoc append**：写 §2.17-§2.20 + §3 组织机构（~25K 字符）
4. `checkDocCompleteness` + `validateDocs` 检查
5. 如缺章节 → 继续 append 补全（不要 overwrite，会丢前文）

**为什么合并写**：
- 每个 writeDoc 调用都带 reasoning_content（思考） + tool_call JSON（结构）
- 20 次往返 = 20 倍元数据浪费
- 合并后 3 次 = 节省 85% 的非内容 token
- 写超 max_tokens 时工具会自动按 `## ` 切分拼接，所以**理论上一次写整张表/全部 API 也行**，但仍要避免超长

**为什么不能写超 max_tokens**：
- 单次 output > max_tokens 会被 `finish_reason=length` 截断
- 截断后 writeDoc 收到不完整内容 → 写入半截文档 → 后面的章节全丢
- 工具会自动按 `## ` 切，但会丢元数据，**你应主动控制在安全范围内**

## 4. 组织机构页面特殊规则

> 组织机构管理页面由系统自带的 `sys_office` 表驱动，**不要重新设计**。
> - 菜单名固定为「组织管理」，路径 `/system/office`
> - 页面列表会展示层级树（pid 自引用）+ 组织类型（type 字典）
> - 不要写字段清单（字段由系统表预定义）
> - 写一句「组织管理使用 sys_office 默认页面」

## 5. 原型草图（ASCII 线框图）

> 每个页面在 ui.md 中必须附带 ASCII 线框草图，让用户/PM 在文字确认前就能**直观看到布局**。

**规则**：
1. 每个页面的「字段/按钮/操作流」段后紧跟一个 ```` ``` ```` 代码块（plain text，不带语言标识）
2. 用 `┌ ┐ └ ┘ ├ ┤ ┬ ┴ ┼` 画框，`─ │` 画线，节点按布局顺序排列（从上到下）
3. 线框必须体现：
   - 查询条件位置（搜索行）
   - 表格/表单位置
   - 按钮位置（新增/编辑/删除等）
   - 分页位置
   - 弹窗/对话框（用虚线 `. . .` 或嵌套框表示）
4. 不允许省略任何页面
5. **不要用 Mermaid / graph TD / flowchart** — 在 markdown 代码块里画 ASCII 框，复制粘贴到 IM 也清晰
6. **线框图必须闭合**——每行 │ 数量一致，代码块 ``` 闭合（避免 LLM 写到一半停）
7. **写 writeDoc append 时必须检查代码块边界**：每个 writeDoc 的 content 末尾必须有偶数个 ```。如果写到最后一个线框图没画完，**先补 ``` 关掉代码块**，下轮 writeDoc 再重新开 ``` 继续画。不要跨边界留未闭合的 ```。（工具会自动补 ``` 来防误判，但最好自己先闭——自动补的内容不一定正确。）

**线框示例**：

**排版要点**：
- 用 `┌ ┐ └ ┘ ├ ┤ ┬ ┴ ┼` 画框，`─ │` 画线
- 搜索行 / 按钮行放在表格**上方**
- 分页放在表格**下方**
- 弹窗另起一个框，跟主页面用空行隔开
- 字段用 `字段名 [控件类型]` 格式，select 写成 `[▼ 选项]`
- 不需要画图工具，VS Code 里手敲就够
